| 操作 | 結果 |

エミュレータで見つけて直したこと
- 中継に届かない間「◯秒前」と判定が止まっていた（同じエラーでは画面が更新されない）→ 1秒ごとに進める。指示を送った応答で状態の古さの基準がずれていた → 基準を分けた
- 手動スキャンの完了から開いた記録が「画面から」と出ていた → 中継の一覧用の情報を使う
- ラベルの「反映待ち」が出ない競合 → Roomの写しを見張る
- 320MHzの局の名前が他の局とぶつかって消えていた → 上辺に沿ってずらす
- 選んでいるチップが色だけで分かりにくい → ✓。記録の絞り込みが4行を占めていた → 横にスクロールする2行
- 見ていないchに今の局のような点が出ていた → 白抜き。見ていないところの一覧を警報より上へ
- PCの起動のイベントで受信ブロックを「自ch」と書いていた → 分けて書く

4. PCが落ちる（SIGKILL）＋中継も止まっている
- 中継を止める → PCの画面から手動スキャン（5GHz）→ 記録はできたが中継へは送る待ち（backlog 1）→ PCを `kill -9` → PCを起動（backlog 1のまま残っていた）→ 中継を起動 → すぐに置かれ、アプリの一覧に出た。

最後に、PC 6件・中継 6件・アプリ 6件の記録とラベルが一致。アプリから2.4GHzを戻す（ON）のも反映した。
中継のRedisのコマンド数は、アプリを前面にしたままで1分に約80（アプリの問い合わせ2秒ごと＋PCの2秒ごと。4.2の上限の範囲）。

M9で直したこと
- アプリの溜まり（ラベル・歩測）の再送は WorkManager の指数的な間隔（15秒から倍）なので、中継が長く止まると戻ってから数分待つことがあった → 問い合わせが失敗から成功に変わったとき（と開いた直後）に、待ちを捨ててすぐ送り直す（要求IDで冪等なので二重にならない）
- 歩測の画面の「未送」が、溜まっているラベルの変更も数えていた → 歩測だけを数え、溜まり全体は別の行に出す

テスト：PC側 206件、中継 23件、アプリ（JVM）10件、すべて成功。

## モニタモードで局を見落とす件の調べ（2026-10-16）

ユーザーの報告：start.sh の2番（モニタモード）だと複数の局を見落とす。1番（スキャンだけ）では見落とさない。
- 記録（events.jsonl・channels.csv）から分かったこと
  - 06:46〜の起動：3分間は2.4/5GHzともよく見えていた（5GHzはスキャンだけより多い17局）。06:49に無線が RF-kill（画面のWi-Fiのスイッチ・機内モード）で止められ、受信停止。そのあと「復旧できない」を8秒ごとに約120件記録していた
  - 06:07〜の起動：全部のchを「見た」のに、フレームが受かったのは5GHz ch48（モニタにする前につながっていたAPのch）だけ。2.4GHzは0局。無線がchを変えていない（A）か、ドライバが radiotap のchを間違えている（B）
- 直したこと：RF-kill を受信停止の理由として出す（復旧の手順を回さない、解けたらやり直す）、起動のスクリプトで RF-kill を先に確かめる、失敗の記録を変わったときだけに、イベントに失敗の理由を出す、NetworkManager から外したあと2秒待つ
- 調べる道具：`hwprobe chancheck`（受けたフレームを捨てずに数え、radiotap のchとビーコンの中身のchをくらべて A／B を判定）、`tools/devpc_monitor_check.sh`（1分ほど、Wi-Fiを戻す、結果を data/devpc/monitor_check.txt に）
- 確認の結果（1回目、2026-10-16 16:39）：モニタモードにすると `iw` は合わせたchを表示するのに、どのch（2.4GHz ch1・6・11、5GHz ch36・48・100）でもフレームが1つも受からない（chで捨てずに数えても0、IFを下げて上げても0）。A でも B でもなく「何も受からない」。本体の起動（15:07）でch48だけ受かったのとも違う（本体は管理モードでパッシブスキャンしてからモニタにする）。道具の既定のchに日本で使えない5GHz ch149を入れていた不具合も直した
- 次：確認のスクリプト第2版（4つのやり方：ふつう／本体と同じ手順／受信フラグ otherbss・control／別のモニタ用IF、tcpdump でも数える、モニタにする前のchも調べる）の結果で、受かるやり方に本体を合わせる
- テスト：PC側 229件
