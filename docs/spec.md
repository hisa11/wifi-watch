# wifiwatch 仕様（全国大会向け）

Oct 14, 2026 · @たまご

ピットに置いたミニPC（AX210）で6GHz帯を中心に受信だけを行い、他チームとの干渉やその他の干渉の兆候を部員のスマホに通知する。

## 目的と前提

大会中、ピットから会場の電波を常時監視し、他チームとの干渉やその他の干渉の兆候を検知して通知する。

- 対象大会：NHK高専ロボコン全国大会（両国国技館）。ほかの大会でも使える作りにする。
- 自チームのロボット通信は6GHz帯。APはロボット本体の片側に付いていて、自分の車体で電波が遮られることがある（地区大会で確認済み）。
- 自リンクの状態は、操縦者スマホ（Pixel 9aか8a）で試合中も常に見られる。本システムでは扱わない。
- 会場のWi-Fiは使えない前提。PCの回線は、専用スマホのUSBテザリング（モバイル通信）。
- 各チームの割当chと予備chは事前に共有される。帯域幅は共有されない。
- 受信専用。送信、パケットの注入、deauthの送信は一切しない。データフレームはMACヘッダだけを見て中身は読まず、通信内容（pcap）も保存しない。
- 検知の目標：対処が要る事象を、人が動ける時間（数十秒〜数分）のうちに検知する。数秒以下の一時的な事象まで取りこぼさないことは目指さない。AX210 1枚の時分割では原理的にできないため。

## 想定する干渉源

6GHz帯での主な相手は②他高専。①と③は「いずれ6GHzに来る」前提で待ち受ける。

| 干渉源 | 特徴（先輩の実測、5GHz帯） | 6GHz帯での状況 | 交渉 | 本システムでの扱い |
| --- | --- | --- | --- | --- |
| ① RoboconFree Wi-Fi（NHKからの委託でNTTが設置？） | 5GHz高域ch100〜144の全chに乱立。客席を覆う配置で、場所とchで強さが変わる | 現時点で不明 | 不可 | 既知の背景。ただし6GHzに初めて出たら1回通知 |
| ② 他高専（無線ヤクザを含む） | 非常に強い。たまに予約外のchで出したり、化け物級に太い帯域で帯域を圧縮したりする | 確実に来る（2.4/5GHzよりまし程度） | 可（譲り合い） | 割当違反と広帯域の検知を最優先 |
| ③ CineEye 2（Accsoon。NHKのフィールドから本部への映像転送） | 桁違いに強い（ch44で約-31dBm）。広帯域。特に2.4GHzを潰す | 現時点では未進出らしい。次回は不明 | 不可（戦ったら負ける） | 6GHzに出たら即crit |

無線ヤクザ：予約済みのch以外で電波を出す、または化け物級に太い帯域で他の帯域を圧縮するWi-Fiとそのチーム。

## 日本の6GHz帯

屋内で使えるのは5925〜6425MHzの24chだけなので、広帯域の局は1台でも影響が大きい。

&#91;embedded content: 日本の6GHz帯 · 20MHzで24ch、160MHzで3本、320MHzで2本\]

どのchも、2本ある320MHzのどちらかには必ず含まれる。

- 320MHz幅は2023年12月に解禁されている（[ITmedia](https://www.itmedia.co.jp/pcuser/spv/2312/22/news133.html)）。
- 6425MHzより上への拡張は、2026年3月の報告（案）でもAFC（周波数の自動調整システム）前提の高出力モードが対象で、屋内向けは含まれない（[総務省](https://www.soumu.go.jp/main_content/001066208.pdf)）。設計はこの24chを前提にする。
- 一番ありそうな無線ヤクザは、Wi-Fi 7ルータを初期設定のまま320MHzで出してしまうケース（推測：320MHzがWi-Fi 7の売りなので、最初から有効な製品がありそう）。
- 6GHz帯ではPMFが必須。

## 構成と役割

監視の本体はピットに置くミニPC 1台で、警報はテザリング回線を通って部員のスマホに届く。スマホの自作アプリからは、Vercelに置いた中継を通してPCを操作できる。

&#91;embedded content: システム構成 · 受信・通知・遠隔操作の8要素\]

AX210は無線が1系統なので、同時に見られるのは1つのチャンネル（幅）だけ。操縦者スマホ（Pixel）には自作アプリを入れ、人に余裕があるときの歩測と、PCの遠隔操作に使う（「スマホアプリと遠隔操作」を参照）。

## アンテナ

内蔵AX210のMHF4端子から2本引き出し、間隔10cm前後のV字（外向きに±45°、V字の面をフィールドに正対）で、高さ1.5〜2mに立てる。

- 種類：Tenmory WiFi 6E トライバンド 5dBi（RP-SMAオス、2.4/5/6GHz）を2本。6GHz帯（5925〜6425MHz）をカバーする6E対応品で、2本とも同じ型番。
- 本数：2本。他チームが2ストリームで送るデータフレームは、受信アンテナが2本ないと復号できない（1本だとビーコンしか確実には見えない）。
- 間隔：10cm前後、6cm未満にしない。10cmは6GHzで約2波長、5GHzで約1.8波長、2.4GHzで約0.8波長にあたる。
- 向き：外向きに±45°傾けたV字にし、V字の面をフィールドに正対させる（フィールドから見て「V」に見える向き）。2本を合成した受信電力は、どの方向・偏波でも縦1本と同等以上になる（下の式）。V字の面に正対する方向では偏波によらず縦1本と同じで、V字の面内から来る横偏波は2本とも受けられない。
- ケーブル：各アンテナとも、AX210のMHF4端子から付属のピグテール（MHF4→RP-SMAメス、25cm、0.81mm）でPC背面のブラケットに出し、RP-SMAの延長（RG58、1m、オス→メス）でアンテナまで伸ばす。2本とも同じ構成にする。6GHzでの損失は接続部込みで約3.75dB（推定。延長なしなら約1.25dB）。
- MHF4端子は抜き差しに弱い。一度付けたら触らず、ケーブルは筐体に固定する。
- 設置：見通しを優先。延長の1mは、アンテナをPCから離して開けた高所に出すために使う。金属の壁・柱・トラスから50cm以上離し、金属の支柱には沿わせない。USB3.0ポートやSSDから離す（2.4GHz帯のノイズ源）。
- 強さの判定には、2本を合成した後のRSSIを使う。片方のアンテナだけの値は、方向と偏波によって-3dBから受信ゼロまで振れる。

2本を合成した受信電力。ψは偏波角、φはV字の面から測った電波の来る方向で、縦1本（偏波が整合）を1とする。

```latex
P \propto \cos^2\psi + \sin^2\psi\,\sin^2\phi \;\ge\; \cos^2\psi
```

### 受信の見込み

- 感度：検出の下限は、等方アンテナに換算して約-91dBm（AX210の感度を-90dBmと仮定、未確認）。屋内の減衰モデル（距離の3乗）で約130m先まで届くので、国技館の広さなら感度で見落とすことはまずない。延長なしなら約156m。
- ピットとフィールドの差：他の電波が自機に効き始めるのは-82dBm（CCAのプリアンブル検出）付近で、検出下限との差は約9dBしかない。ピットとの間にだけ壁や人の群れが入ると、フィールドで効く局がピットから見えなくなる。自チームの試合中に、ピットで自APのRSSIを記録して実測する。ロボットに載った自APが、フィールド側の基準の電波源になる。
- 強い電波：CineEye（ch44で-31dBm、先輩の測定値を0dBi基準と仮定）に合わせたとき、AX210への入力は約-30dBm。規格の最大入力（-30dBm）と同じくらいで、実チップにはもっと余裕があるはず（未確認）。6GHzの受信には影響しない。

## 監視方式

AX210は無線が1系統なので、自分のchを含む160MHzブロックを160MHz幅で受信しつつ、局を見つけるための20MHz巡回を挟む。

### 起動前の確認（合否ゲート）

AX210を6GHzでモニタモードにできるかを先に確かめる。Ubuntuで6GHzのAPへの接続と通信は確認済みで、モニタモードは未確認。IF名は環境に合わせる。モニタにする前に管理モードで一度スキャンし、周りのビーコンの国情報で6GHzを有効にさせる（推測：Intelのファームは、周りの国情報で6GHzを有効にするLARという方式のため）。

```bash
uname -r
sudo ip link set wlan0 up
sudo iw dev wlan0 scan > /dev/null   # 管理モードでスキャンし、周りの国情報を拾わせる
iw reg get                           # phy側が country JP で、5925〜6425MHz が並ぶか
iw list | grep -E "\* (59[2-9]|6[0-9]{3}|70[0-9]{2})"
sudo ip link set wlan0 down && sudo iw dev wlan0 set type monitor && sudo ip link set wlan0 up
sudo iw dev wlan0 set freq 5955
```

6GHzの周波数が disabled なしで並び、最後のコマンドが通れば合格。不合格なら管理モードのパッシブスキャン（`iw dev wlan0 scan`）に切り替える。その場合に動くのはビーコンから分かる機能（局の一覧、占有表示、帯域幅、割当違反、署名による検知）だけで、活動量・リトライ率・deauth・160MHz受信は使えない。

管理モードのスキャンは、6GHzではPSCと、2.4/5GHzのRNRで知ったchに限られる可能性がある（推測）。その場合、PSC以外に単独で出る局は見落とす。

### 受信の仕方（LIVEモード）

- 自分のchを含む160MHzブロック（ch1〜29、33〜61、65〜93のどれか）を、主20MHzを自分のchにして160MHz幅で受信し、自分のchにかかる広帯域の送信を拾う。デコードできるのは、自分の主20MHzを含む送信だけ。ブロック内の別chを主chにする局のビーコンや、別chだけで出る20MHzの送信は、この受信では入らない（受信機は主20MHzでパケットを検出するため）。他局の160MHz送信をこの方法で受信できるかは未検証。
- 局を見つける20MHzの巡回は、全帯域（2.4/5/6GHz）が対象。優先は、自ブロック内の別ch（7ch）→ PSC（ch5/21/37/53/69/85）→ その他の6GHz → 5GHz → 2.4GHzの順。自ブロック内の別chの局は自分と一番重なるのに、160MHz受信では見つからないので最優先にする。
- 時間配分（暫定）：10秒周期で、自ブロックの160MHz受信7秒＋250msの巡回12枠。自chの受信率は70%。内訳と、局を見つけるまでの時間は下の表。
- 予備chが5GHzのときは、5GHz枠の1つを予備ch専用にする（10秒ごとに見る）。逃げると決めるときに、逃げ先の状態が新しいものになる。その分、他の5GHzの局の発見は平均約48秒・95%で約92秒に延びる。
- 帯域幅は、ビーコンのHE Operation（6GHz Operation Information）とEHT Operation要素から読む。AX210は320MHzの送信そのものは受信できないが、宣言された幅は読める（未確認）。
- 6GHzの局のchは、受信した周波数ではなく、HE Operationに書かれた主chで決める。重複ビーコン（Duplicate Beacon、未確認）を出す局は、主ch以外のchでも受信されるため。
- チャンネル切替は200ms未満の間隔にしない。

| 巡回の対象 | ch数 | 割り当て（10秒あたり） | 再訪の間隔（最大） | 常駐する局の発見（平均／95%） | 5秒の事象を捕まえる確率 |
| --- | --- | --- | --- | --- | --- |
| 自ch（主20MHz、160MHz受信） | 1 | 7秒 | 10秒 | 3秒以内 | 100% |
| 自ブロック内の別ch | 7 | 4枠 | 約20秒 | 約10秒／約19秒 | 約30% |
| 6GHzのその他 | 16 | 4枠 | 40秒 | 約21秒／約38秒 | 約13% |
| 5GHz | 20 | 3枠 | 約70秒 | 約34秒／約66秒 | 約8% |
| 2.4GHz | 13 | 1枠 | 130秒 | 約66秒／約125秒 | 約4% |

1枠250msのうち、chの切替に30msかかると仮定した（推定）。1枠でビーコンを2〜3回受けられる。

### モード（ダッシュボードから切替）

| モード | 使う場面 | 動作 |
| --- | --- | --- |
| PRE | 大会前・試合前の下見 | 2.4/5/6GHzの全ch（57ch）を巡回し、1周約14秒。約5分でしきい値を較正し、全帯域を一度は見る |
| LIVE | 既定 | 上の「受信の仕方」 |
| QUIET | 山場の試合 | 自ブロックの160MHz受信を主にし、巡回は自ブロック内の別ch（10秒あたり1秒）と生存確認（30秒ごとに5GHzを250ms）だけ残す。自chの受信率は約89% |

### 手動スキャン

デスクトップの画面かスマホアプリから、1回だけのスキャンを指示できる。結果は「記録」として残り、あとからラベルを付けられる（「記録とラベル」）。

- 対象：既定は、巡回に入っている帯域の全ch。帯域やchを選んで絞れる。
- 1chあたり250ms（巡回と同じ）。全57chで約14秒、6GHzだけ（24ch）なら約6秒。
- 実行中は自ブロックの受信と巡回を止め、終わったら元のモードに戻る。画面とアプリに「手動スキャン中（残り何秒）」と出す。
- 同時に走るのは1つだけ。実行中に来た指示は断る。
- QUIETのときは、実行前に確認を求める。山場の試合中に、自chを見ない時間ができるため。
- 結果：chごとの占有と、局ごとのSSID・BSSID・ch・帯域幅・RSSI・規格・機種推定。いつ、どこから（画面かアプリか）指示したかも残す。

### 巡回の帯域ON/OFF

帯域（2.4/5/6GHz）ごと、またはchごとに、巡回から外したり戻したりできる。デスクトップの画面とスマホアプリのどちらからでも操作でき、再起動しても設定は残る。

- 外した帯域の巡回枠は、残りの巡回先に配り直す。自ブロック内の別chの4枠は動かさない。
- 自ブロック（自分のchを含む160MHz）は外せない。
- 生存確認は止めない。2.4/5GHzを両方外したときは、QUIETと同じく30秒ごとに5GHzを250ms覗く。受信停止の誤報を防ぐため。
- 外した帯域とchは、画面とアプリに灰色の「巡回外」と出し、「検知なし」と区別する。見ていない帯域を、何もないと誤解させないため。
- 手動スキャンの既定の対象からも外れる。指定すれば、外した帯域もスキャンできる。
- 変更はイベントとして残す（いつ、どこから、何を）。

## 歩測（Pixel・移動計測）

据え置きのPCから見えない場所の電波状況を確かめるため、Pixelを持って会場を歩いて測る。常時はできない（Pixelが操縦者スマホのため）が、実施自体は必須。

- 目的：ピットから死角になる場所（フィールド際、遠い隅、観客側）の電波を、地点ラベル付きで記録する。据え置き監視を補完する。
- タイミング：人に余裕があるとき。自チームの試合中はしない（Pixelが操縦者スマホになる）。下見・待ち時間に行う。
- 方法：自作アプリでスキャンし、SSID・BSSID・周波数・帯域幅・RSSIと、取れればIE（HE/EHT Operation）を、地点ラベル付きの「記録」として残す。固定の高さと向きで、1地点30〜60秒（未確認）。
- 持ち帰り：PCにつながればアプリから送る。つながらなければアプリ内に残してあとで送り、JSONでの書き出しもできる。PC側で地図化し、据え置きの監視と突き合わせる。
- スキャン回数の制限は、開発者オプションで解除済み。
- 先に確認（未確認）：①アプリのスキャンが毎回新しい結果を返すか（結果の時刻が更新されるか）。②Pixel 9a/8a の一覧に6GHz APが出るか（国設定で無効なことがある）。③PSC以外のchに単独で出る6GHz局が一覧に出るか（Androidの6GHzスキャンは、PSCとRNRで知ったchに限られる可能性がある。推測。自チームのルータをch9などに置いて試す）。

## スマホアプリと遠隔操作

自作のAndroidアプリで、歩測・PCの遠隔操作・記録の閲覧とラベル付けをする。デスクトップの画面でできる手動スキャン、帯域ON/OFF、記録の閲覧とラベル付けは、同じものがアプリからもできる。

- 入れる端末：操縦者スマホ（Pixel 9a/8a）。ほかの部員のAndroidにも入れられる。
- 機能：
  - 歩測（「歩測」を参照）
  - 遠隔の手動スキャン（「監視方式」の「手動スキャン」）
  - 巡回の帯域ON/OFF（「監視方式」の「巡回の帯域ON/OFF」）
  - 記録の閲覧とラベル付け（「記録とラベル」）
  - PCの状態の表示：モード、巡回中の帯域、発生中の警報
- 自チームの試合中は使わない。Pixelが操縦者スマホになるため。

### 経路と安全

PCはテザリングの携帯回線の内側にいて、外から直接は届かない。そこでVercelに中継（APIと保存先）を置き、アプリもPCも外向きにそこへつなぐ。PCは数秒おきに中継へ取りに行き、指示を受けて実行し、結果と状態を中継に置く。VPNは使わない。

- PCは外からの接続を受けない。PCのAPIと画面は127.0.0.1だけで、デスクトップの画面専用。遠隔の操作はすべて中継を通す。
- 問い合わせの間隔：アプリを開いていないときは10秒、開いているときは2秒（暫定）。アプリからの指示は、この間隔のうちにPCに届く。
- 待機中の問い合わせは、Redisの1コマンド（受信箱の版数を見るだけ）に抑える。1回に3コマンド使う作りだと、つけっぱなしで月の無料枠を超える。
- 中継に置くもの：まだ実行していない指示、PCの最新の状態（アプリを開いている間だけ更新）、記録とラベルの写し、アプリから送られた歩測の記録とラベルの変更。
- 保存先：Upstash Redis（Vercelのマーケットプレイスからつなぐ）。
- トークンはアプリ用とPC用に分ける。アプリ用のトークンではPCの役はできない。中継が受ける指示は決まった種類（手動スキャン、帯域ON/OFF）だけで、値も検査する。
- アプリの通信はモバイル回線を指定して行う。ロボットのWi-Fi（インターネットなし）には流さず、操縦用アプリにも干渉しない。
- 回線がないとき、アプリは歩測の記録とラベルの変更を端末に溜め、つながったら送る。PCも、送れなかった結果を溜めて再送する。同じ指示が二重に届いても、結果が変わらないようにする。
- 指示には60秒の期限を付ける。PCが受け取らないまま60秒を過ぎた指示は実行せず、アプリに「PCに届かなかった」と出す。回線が戻ったあとで、古い手動スキャンが試合中に走るのを防ぐため。
- 無料枠（Vercel Hobby、Upstashの無料プラン）の見込み：大会4日（1日14時間稼働、アプリを開くのは1日3時間）で、いちばん厳しいUpstashのコマンド数が月の枠の約29%、ほかは6%以下（PCが置く状態の写しを1回8KB以下にした場合。Upstashの帯域は約4%）。30日つけっぱなしでも約52%。
- Hobbyは非商用に限られる。部の道具として使う分には当たらない（推測）。

| --- | --- | --- |
| PCの手動スキャン | ミニPC（AX210） | chごとの占有、局ごとのSSID・BSSID・ch・帯域幅・RSSI・規格・機種推定 |
| 歩測 | 自作アプリ（スマホのWi-Fi） | 局ごとのSSID・BSSID・周波数・帯域幅・RSSI、取れればIE |

- どの記録にも、時刻、取った機器、指示した場所（画面かアプリか）、スキャンの設定を付ける。
- ラベル：場所、タグ、メモ。場所はよく使うものを選択肢から選べる（例：ピット、フィールド北、客席東）。あとから何度でも直せる。
- 見る：一覧（種類・日時・場所・帯域で絞り込み）と詳細（局の表と、chごとのグラフ）。
- 保存：PCが正本。アプリは自分の歩測の記録と、見た記録の写しを持つ。ラベルを両方で直したときは、新しい方を残す。中継には写しを置き、アプリはそこから見る。
- 書き出し：JSONとCSV。
- 通信の中身は記録しない。ビーコンとヘッダから分かることだけ。

## 検知と警報

警報はすべて「ピットから見えたもの」で判定する。警報が出ないことは安全を意味しないので、画面には「安全」ではなく「検知なし」と出す。しきい値はすべて暫定で、PREモードの下見で較正する。

| 警報 | 条件 | レベル |
| --- | --- | --- |
| 割当違反（予約外ch） | チームが分かっている局が、そのチームの割当ch・予備ch以外で出ている | warn（暫定） |
| 割当違反（帯域の食い込み） | 宣言された帯域幅が、他チームの予約chにかかっている（160/320MHzを含む） | warn（暫定） |
| 新規参入×重なり | 自分の帯域に重なる局が新しく現れた（過去10分に未観測のBSSID、または既知の局がchを移して重なった）。チーム名・機種推定・ch・強さを添える。強さは参考表示で、判定には使わない | warn（暫定） |
| 正体不明の強力局・広帯域局 | 所属不明で、160MHz以上、または6GHz内の他局の中央値より20dB以上強い。6GHz内の局が5未満のときは-45dBm以上で判定 | warn（暫定） |
| RoboconFreeの6GHz出現 | 署名に一致する局を6GHzで初めて観測 | 1回だけ通知（warn、暫定） |
| CineEyeの6GHz出現 | 署名に一致する局を6GHzで観測 | crit |
| 活動量の急増 | 自分の帯域のフレーム数を、実際に受信していた秒数で割った値が、過去10分の中央値の3倍以上かつ100/秒以上。chごとに数え、基準も同じ単位で持つ（時計の秒で割ると、PREからLIVEへの切替だけで見かけ40倍になり必ず鳴る） | warn |
| リトライ率 | 自分の帯域のリトライ率が30%以上（10秒で50フレーム以上あるとき） | warn |
| 同名SSIDの別AP | 自分と同じSSIDで別のBSSID（なりすまし、または設定漏れ） | crit |
| deauth/disassocの洪水 | 自分のアドレスを含むものが3秒で10個以上 | 自分のAPのPMFが必須ならwarn（6GHzは常に必須）、そうでなければcrit |
| 受信停止 | 巡回の2.4/5GHz枠で1件も受信しない周期が2回続いたら、モニタを再設定する。戻らなければiwlwifiを読み込み直し、管理モードでスキャン→国設定がJPで6GHzが有効か確認→モニタ、の順に戻す。それでも戻らなければ通知。自chが静かなこと自体は故障とみなさない（静かな6GHzでは正常なため） | crit |

正体不明の局は、ダッシュボードでチーム名を付けると、以後は割当違反の判定に回る。20dBの根拠は、先輩のスライドでCineEyeが2番目に強い局より約22dB強かったこと。

## 機種推定と分類

各局を「誰の、何の機器か」と「交渉できる相手か」で分類し、交渉できるかどうかで色分けする（他高専＝黄、RoboconFreeとCineEye＝赤）。

- 署名ファイル `signatures.json`：SSIDのパターン、OUI、種類（公式インフラ／放送機材／チーム／不明）、交渉可否を持つ。次の魔物はコードを触らずに追記する。
- 初期の署名：`ROBOCON_Free_Wi-Fi*` と `ROBOCON_Staff*` は公式インフラ（交渉不可）、`CineEye*` は放送機材（交渉不可）。6GHz版のSSIDとOUIは、見つけ次第追加する。
- スライドでCineEyeと同じ画面に写っていた「GEAR Arx6duc2」は正体不明なので、署名には入れず未分類とする。
- チームの割当て：configの対応表（BSSID・SSIDからチーム名）と、ダッシュボードでの手動タグ付け。既知で問題のない局（ピットのAPなど）は `known_ok_bssids` に入れ、新規参入の誤報を防ぐ。
- 機種推定に使う情報：
  - OUI（`ieee-data`）、WPSのメーカー名と型番
  - 規格（n/ac/ax/be）、暗号方式とPMF
  - IE構成の指紋、ベンダ固有IEから分かるチップの手がかり
  - ランダムMACの判定、SSIDの傾向（スマホのテザリング、Wi-Fi Direct、ESP系、Raspberry Pi）
  - HEのBSS Color、HE Capabilitiesの指紋、国コード
  - RNR（IE201）による、2.4/5/6GHzにまたがる同一機器の紐付け

## 通知

ntfy.shとDiscord Webhookの2経路で、部員の個人スマホに通知する。critは両方へ同時に送り、それ以外はntfyだけに送る。

| 種類 | ntfyの優先度 | 送り先 |
| --- | --- | --- |
| crit | 5 | ntfyとDiscord |
| warn | 4 | ntfy |
| 解消 | 2 | ntfy |
| 稼働中（起動時と15分ごと） | 1（最低） | ntfy |

- 抑制：同じ警報は30秒以内に再通知しない。当事者（局）が増えたときだけ「追加」として再通知する。条件が10秒消えたら解消を通知する。
- 再送：回線が切れている間も、critとwarnは復帰するまで無期限に再送する。
- 受信側：部員の個人スマホでntfyアプリから同じトピックを購読する（複数台可）。「即時配信」を有効にし、バッテリー最適化から外し、最高優先度はおやすみモードを突破できるようにする。
- 操縦者スマホ（Pixel）は通知の対象に含めない。
- トピック名は推測されにくい文字列にする。ntfyの自前サーバは立てない。

### 回線が止まったとき

ntfyとDiscordは同じテザリング用スマホと携帯網を通るので、両方同時に止まりうる。15分ごとの稼働通知だけでは気づくのが遅れるため、次の3つで備える。

- 外部の死活監視サービス（healthchecks.ioなど、未確認）に1分ごとに生存報告を送り、3分途絶えたらサービス側から部員に通知させる。
- ピットでは、critのときに音を鳴らす（回線が要らない）。手持ちのSTM32にブザーを付け、USBシリアルで鳴らす形でもよい。
- テザリング用スマホのWi-FiとBluetoothは切っておく。自分で電波を増やさないため。

## ダッシュボード・ログ・運用

ダッシュボードはPC上のブラウザで見る（127.0.0.1:8080、1秒ごとに更新）。画面はPC上でだけ開く。遠隔ではアプリを使う（「スマホアプリと遠隔操作」）。

- 表示：発生中の警報、チャンネルごとの占有、局の一覧と機種推定、端末の一覧、イベント履歴、記録の一覧。巡回から外した帯域は灰色で「巡回外」と出す。
- 他チームの問題チャンネル：強い局（-70dBm以上、暫定）が3つ以上重なるchを強調する。
- 回避先の提案：自分の帯域幅で占有の少ない候補を上位3つ出す。ピットから見た参考値として扱う。
- 操作：モードの切替、自分のchの変更（再起動なし）、局へのチーム名の手動タグ付け、手動スキャン、巡回の帯域ON/OFF、記録のラベル付け。

### 表示の速さ（リロード）

- アナライザーのグラフ（チャンネル別の占有）を最優先の表示にし、1秒ごとに更新する。
- バックエンドは常時動いて最新の占有状態を持つので、ブラウザを再読込すると直近のグラフが即座に出る。
- 初回起動（コールドスタート）時は、6GHzの自分のブロックとPSCを短い滞在で先に1周し、グラフを約5秒で出す。残りの帯域は順次埋める。

### ログ

- `events.jsonl`：警報と解消のイベント。
- `channels.csv`：10秒ごとの帯域別の占有。
- 通信内容（pcap）は保存しない。

### 運用

- 事前準備：`config.json` に、自チームのSSID・BSSID・端末のMAC・割当ch・予備ch、各チームの予約表、チームの対応表、`known_ok_bssids`、ntfyのトピック、Discord Webhookを書く。
- 起動：wlan0をNetworkManagerの管理外にし、合否ゲートと同じく先に管理モードでスキャンしてからモニタモードにし、`sudo pm2` で常駐させる。
- Vercel：中継をデプロイしてUpstash Redisをつなぎ、アプリ用とPC用のトークンを決める。アプリには中継のURLとアプリ用のトークン、PCには中継のURLとPC用のトークンを設定する。
- 中継の関数は東京（hnd1）で動かす。既定はワシントンD.C.（iad1）で、そのままだと問い合わせのたびに太平洋を往復する。Upstashも東京に置く（無料プランで選べるかは未確認）。
- 会場で：PREモードで約5分下見し、しきい値を較正する。

## 対象外と限界

ピットから受信だけで見ているので、見えないものは判定できない。

- 自分のリンクの品質は扱わない（操縦者スマホで見る）。
- フィールド上だけで起きている干渉は見えないことがある（死角の一部は歩測でおぎなう）。ピットとフィールドの差に使える余裕は約9dBしかない（「アンテナ」の「受信の見込み」）。
- Wi-Fi以外の干渉はほぼ見えない。`iw dev wlan0 survey dump`（busyとnoise）と `iw dev wlan0 set monitor fcsfail`（壊れたフレームの数）が使えれば、代わりの指標にする。
- 320MHzの送信（Wi-Fi 7のEHT）そのものは受信できない。根拠はビーコンで宣言された幅だけになる。
- 巡回で見ているchでは、短い送信を取りこぼす。5秒の事象を1回でも捕まえる確率は、自ch 100%、自ブロック内の別ch 約30%、6GHzのその他 約13%、5GHz 約8%、2.4GHz 約4%（LIVEの暫定配分）。
- 送信しないので、距離の測定や能動的な調査はしない。
- 自ブロック内の別chだけで出る20MHzの送信は、160MHz受信では数えられない（巡回の250msの間だけ見える）。活動量とリトライ率は、自分の主20MHzにかかる送信の値になる。
- 6GHzでだけ出ている局は、型番まで分からないことが多い。6GHzはWPA3/OWEが必須で、PSKを配る仕組みのWPSを持たないため。RNRで2.4/5GHz側と紐付けられたときだけ精度が出る。
- 仮説：6GHz帯のすぐ上と下は放送事業用（境界は未確認）。NHK中継の無線回線が会場に出ていれば、ch1付近やch93付近にWi-Fi以外の隣接干渉が出うる。AX210では見えないので、帯域の端のchだけ原因不明の不調が出たら、まずこれを疑う。
- 手動スキャン中は自ブロックを受信しない（全帯域で約14秒、6GHzだけで約6秒）。
- 巡回から外した帯域とchは見ていない。そこで起きたことは検知できない。
- 遠隔操作は、携帯回線とVercel・Upstashが動いているときだけ使える。止まっても、監視と通知（ntfy・Discord）は動く。

## 削除・却下した案

検討の途中で外した案と、その理由。同じ案を再検討するときの参考にする。

| 案 | 外した理由 |
| --- | --- |
| USBアダプタ2本の構成（自分のchに固定＋巡回） | 使えるのは内蔵のAX210 1枚だけのため |
| 自分のAPの監視（ビーコンの途絶・欠落、チャンネル変更、遮蔽の判定、自端末の沈黙、未登録端末の接続） | ロボットはピットから常に見えるわけではなく、自分のリンクは操縦者スマホで見られるため |
| アンテナを操縦者の近くに置く | ピットから動かせないPCには当てはまらないため |
| ロボットを回して死角を測る | 見ればだいたい分かるため |
| ミニPCを発信機にした距離の測定 | AX210は監視とAPを同時にできない見込みで、自分の電波も増えるため |
| ntfyの自前サーバ | 会場からの到達性とiPhone向け設定の手間に見合わないため |
| GEAR Arx6duc2を交渉不可の署名に入れる | 根拠がなく、正体不明のため |
| アンテナ1本 | 2ストリームのデータフレームを復号できないため |
| 受信停止を「5秒フレームなし」で判定する | 静かな6GHzでは正常でも鳴るため。その後の読み込み直しで、6GHzが無効のまま戻らないおそれもある |
| 局を見つける巡回でPSCを最優先にする | 自分と一番重なる、自ブロック内の別chの局を見つけるのが遅れるため |
| Termux（termux-wifi-scaninfo）での歩測 | 自作アプリに決めたため。歩測・遠隔操作・記録の閲覧とラベル付けを1つのアプリにまとめる |
| ntfyを遠隔操作の命令の経路に使う | 公開トピックなので署名と暗号化が要り、送れる量も小さく、記録の閲覧もできないため |
| Tailscale（VPN）でPCに直接つなぐ | 操縦用アプリと干渉し、準備も手間なため |
| VercelのWebSocketで常時つなぐ | 公開ベータで、Hobbyは1接続が最大300秒。つないでいる間はメモリの課金が続き、既定の2GBだと約7.5日で月の無料枠を使い切るため |

## 実機確認・未決事項

大会前に実機で確かめることと、まだ決めていないこと。

### 実機で確かめる

- [ ] AX210を6GHzでモニタモードにできるか（「監視方式」の合否ゲート）
- [ ] ビーコンからEHT Operation（320MHzの幅）を読めるか
- [ ] 160MHz幅のモニタで、他局の160MHz送信を受信できるか
- [ ] `survey dump` と `fcsfail` が使えるか
- [ ] 頻繁なチャンネル切替でAX210のファームウェアが不安定にならないか
- [ ] アンテナとケーブルの6GHzでの実際の損失
- [ ] Pixel 9a/8a の一覧に6GHz APが出るか
- [ ] アプリのスキャンが毎回新しい結果を返すか（結果の時刻が更新されるか）
- [ ] iwlwifiを読み込み直した直後に、6GHzの周波数が disabled になるか（`sudo modprobe -r iwlmvm iwlwifi && sudo modprobe iwlwifi` の後に `iw list`）
- [ ] 自チームの試合中にピットから自APのRSSIを記録し、ピットとフィールドの差が約9dBの余裕に収まるか
- [ ] PixelがPSC以外のchに単独で出る6GHz局を一覧に出すか（自チームのルータをch9などに置く）
- [ ] テザリングを切ったとき、外部の死活監視が3分で部員に通知するか
- [ ] アプリからの指示が、中継を通ってPCに何秒で届くか（テザリング回線越し）
- [ ] PixelのスキャンでIE（HE/EHT Operation）が取れるか
- [ ] ロボットのWi-Fiにつないだまま、自作アプリがモバイル回線で中継に届くか（操縦用アプリと同時に使って確かめる）

### 未決

- [ ] 自チームの予備chが6GHzか5GHzか（5GHz枠の1つを予備ch専用にするかが決まる）
- [ ] LIVEの時間配分：暫定は自ブロック7秒＋巡回12枠。自ブロック5秒＋巡回20枠にすると、6GHzの局の発見が約1.7倍速くなる（95%で、自ブロック内の別ch 19秒→10秒、6GHzのその他 38秒→25秒）代わりに、自chの受信率は70%→50%に下がる
- [ ] 表で「暫定」とした警報のレベルとしきい値
- [ ] 同じ局に複数の警報が重なったときのまとめ方
- [ ] RoboconFreeとCineEyeの6GHz版のSSIDとOUI（見つけ次第 `signatures.json` に追加）
- [ ] 大会規定で、監視PC・外付けアンテナ・テザリングの使用が認められるか
- [ ] 中継への問い合わせ間隔（暫定：アプリなし10秒、アプリあり2秒）
