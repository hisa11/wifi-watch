## 無線・解析

- **chの書き方** — 設定では `"6g37"`・`"5g36"`・`"2g1"`・`"6GHz ch37"`・MHzの整数を受け付け、内部はすべてMHz。日本で使えないch（6GHzの偶数ch、5GHzのch149以上など）は読み込みで止める。
- **日本の5GHz** — W52/W53/W56の20ch（ch144を含む）。束ねられるのは40MHz（10本）、80MHz（36・52・100・116・132）、160MHz（36・100）。ch132〜144は80MHzまで。
- **自ブロック** — 自分のchを含む160MHzブロック。無ければ80→40→20MHz（予備chや自分のchが5GHzのch132〜144のとき）。
- **320MHzが2本候補になるch（ch33〜61）** — 局の範囲はEHT OperationのCCFS1で決める。束ね方の表から選ぶときは低い方（中心ch31）。
- **強さの合成** — アンテナごとの値（radiotapの2つ目以降の名前空間）があれば電力の和で合成し、無ければドライバが最初の名前空間に入れた値を使う。推測：iwlwifiの最初の値は2本の強い方で、和ではない（未確認）。
- **主chと幅の優先** — 幅はEHT Operation（情報あり）→ HE Operationの6GHz情報 → VHT Operation → HT Operation。6GHzのHE 6GHz情報で160MHzかつCCFS1=0のときは、CCFS0が160MHzブロックの中心なら160MHz、そうでなければ80MHzとみなす。IEが主chと矛盾したら20MHzとみなし「疑わしい」印を付ける。
- **Multiple BSSID（IE 71）の非送信BSS** — 今は展開しない（送信BSSだけ局の表に載る）。6GHzで1台が複数SSIDを出す場合、2つ目以降のSSIDは見えない。必要になったら追加する（提案）。

- **カーネル内の切り詰め（BPF）** — AF_PACKETのソケットにclassic BPFを付け、データフレームはMACヘッダの長さちょうど、制御フレームは16バイト、ビーコンとプローブ応答以外の管理フレームは32バイト（理由コードまで）に切り詰める。ペイロードはユーザ空間に来ない。そのため解析はFCSをヘッダの読みでは差し引かず、本文を読む管理フレームでだけ差し引く。
- **リトライ率の数え方** — 分母は「データフレームと、ビーコン以外の管理フレーム」。制御フレーム（Retryビットを持たない）とビーコン（再送されない）は除く。
- **自分のフレームを除く** — 自APのBSSIDと自端末のMAC（config の own.bssids・own.station_macs）を含むフレームは、活動量とリトライ率から除く。自リンクの状態は扱わない（仕様書）ため、他局の活動として数える。
- **IEの全部の解析は局ごとに5秒に1回** — それ以外のビーコンでは強さと時刻だけ更新する（処理能力のため）。
- **プローブ要求の本文（端末が探しているSSID）は読まない** — 端末の持つネットワーク名が分かってしまうため。端末の一覧はデータフレームのヘッダだけから作る。
- **統計の鍵は (主chのMHz, 受信の幅)** — 20MHzで受けたときと160MHzで受けたときは別に数え、基準も別に持つ（仕様書「chごとに数え、基準も同じ単位で持つ」）。

## 巡回（M2）

- **自ブロックの7秒を4つに分ける** — LIVEの10秒周期は「自ブロック1.75秒＋巡回3枠」を4回。自chから離れる時間は最大0.75秒（連続7秒＋3秒より短い）。切替の回数が増える分、実際の受信率は68.8%（割り当ては70%）。仕様書は配置を決めていないため。
- **外した帯域の枠の配り直し** — 1枠ずつ「ch数÷枠数（再訪の間隔）がいちばん長い組」に渡す。組のch数より多くは渡さない。渡す先が無ければ自ブロックの受信に戻す。自ブロック内の別chの枠と予備chの専用枠は動かさない。
- **QUIETの形** — 10秒周期で自ブロック内の別ch 4枠（1秒）、3周期（30秒）に1回だけ5GHzの生存確認を250ms。割り当ては89.2%、切替を除いた実測は88.0%。
- **予備chの専用枠** — 予備chが5GHz（自ブロック外）のとき、5GHzの3枠のうち1枠を専用にし、その予備chは5GHzの巡回の順番から外す。予備chを巡回から外した場合は専用枠も無くす（利用者の選択を優先）。
- **自ブロックのある帯域を外したとき** — 例えば6GHzを外しても自ブロック（160MHz）は見続け、それ以外の6GHzのchだけ巡回から外す（仕様書「自ブロックは外せない」）。自ブロックのchを個別に外す要求は断る。
- **生存確認の「周期」** — LIVEは10秒周期の2.4/5GHzの枠、QUIETと2.4/5GHzを両方外したときは30秒ごとの5GHzの生存確認、PREは1周。生存確認のchは、最近いちばん多く局が見えた5GHzのch（M3でつなぐ）。
- **初回起動の先回り** — 自ブロック（160MHz）、自ブロック内の別ch、自ブロック外のPSCを200msずつ（6GHz ch37なら12枠＝2.4秒）。
- **手動スキャンの順番** — 仕様書の優先の順（自ブロック → PSC → 6GHzのその他 → 5GHz → 2.4GHz）。既定の対象は巡回に入っているch、帯域やchを指定すれば巡回外も可。
- **PREと巡回外** — PREも巡回なので、外した帯域・chは見ない（自ブロックは見る）。2.4/5GHzを両方外したPREでは、30秒に1回5GHzの生存確認を挟む。
- **長い枠の区切り** — 自ブロックの1.75秒は0.5秒ずつ解析に渡す（画面と警報の更新を遅らせない）。同じ設定が続くときはtuneし直さない。
- **tuneに失敗したとき** — その枠の時間は待って次へ進む（空回りしない）。失敗の続きは受信停止の判定（M3）で扱う。

## 警報（M3）

- **警報のまとめ方（未決への仮定）** — 鍵は「種類:範囲」。割当違反2種はチームごと、新規参入は自分の帯域で1つ、正体不明の局は帯域ごと、署名は署名ごと、活動量とリトライ率は自chごと、同名SSIDはSSIDごと、deauthは自分で1つ、受信停止は1つ。同じ局に違う種類の警報が重なっても通知はまとめない（種類ごとに1通）。画面では局ごとに関係する警報を並べる（M5）。
- **通知のタイミング** — 発生（raised）は通知。当事者が最後に知らせたより増えたら「追加」を30秒以内でも通知。条件が10秒消えたら cleared（記録だけ）、解消の通知は「最後に発生・追加を知らせてから30秒」以降に出す。出す前に再び成り立てば、発生も解消も知らせない。これで同じ警報を30秒以内に重ねて知らせず、利用者が「解消した」と誤解する時間も作らない。
- **新規参入の基準** — 起動直後に見えた局は新規にしない：局の主ch（または受けたch）を0.15秒以上見たことがあってから現れた局だけを新規とする。10分以上見えなかった局が戻った場合と、自分の帯域の外から重なる位置にchを移した場合も新規。新規の扱いは10分（その間いて重なっている限り当事者）。自分の帯域＝自分のch×config の own.width。
- **局が「いる」とみなす時間** — 最後に見てから、そのchの再訪の間隔の2.5倍（最低60秒）。巡回外のchは600秒。
- **割当違反の対象** — チームが分かっている局（config・手動タグ・SSIDのパターン・RNR）だけ。予約ch＝割当ch＋予備ch。帯域の食い込みは、局の宣言した範囲が他チーム（自チームを含む）の予約chの20MHzにかかるとき。
- **正体不明の局を見る帯域** — 6GHzと、自分のch・予備chのある帯域。中央値は同じ帯域の他局（自APを除く）の強さ（指数移動平均）で計算。
- **RoboconFreeの6GHz出現** — 画面では成り立つ間「発生中」として出し、通知は署名ごとに一度だけ（再起動しても覚える。保存はM5）。
- **活動量の窓** — 今の値は直近の10秒の桶2つ（10〜20秒ぶん）で、受信が2秒以上あるとき。基準は過去10分の10秒の桶（受信0.5秒以上）の中央値で、桶が3つ以上あるときだけ判定。鍵は (自ch, 受信の幅) で、PREは20MHz、LIVE/QUIETは自ブロックの幅。
- **deauthのPMF** — 自APのビーコンのRSN（MFPR）→ config の own.pmf_required → 6GHzなら必須、の順で決める。
- **同名SSIDの別AP** — config の own.bssids が書かれているときだけ判定（無いとどれが本物か分からない）。自チームの判定もBSSIDが書かれていればBSSIDで行う。
- **受信停止の追加の条件** — 自ブロックへのtuneが3回続けて失敗したとき（6GHzが無効になった等）も同じ復旧の手順に入る。失敗（crit）のあとも5分ごとに復旧を試みる。周期の判定は、その周期の最後の生存確認の枠が終わった時点で行う。
- **PREの較正** — しきい値は自動で書き換えない。PREで約5分（1周以上）たったら、帯域ごとの局の数・強さの分布・強い局が重なるch・自chの活動量と、今のしきい値でどう判定されるかの説明を作り、画面に出す（人がconfigを直す判断に使う）。

## 偽の無線のモデル（実機で確かめるまでの仮定）

- 受信機は主20MHzで検出する。20MHzのビーコンは局の主chでだけ聞こえる。重複ビーコンの局は局の帯域内のどの20MHzでも聞こえる。
- データは局の全幅で送る。受信機の主20MHzが局の範囲内で、局の範囲が受信の幅に収まるときだけ聞こえる（160MHz受信で他局の160MHz送信が受信できる、は未検証の仮定）。320MHzのデータは聞こえない。
- ACKは局の帯域に重複して送る。
- 切替に30ms、感度-91dBm。

## 設定

- **再起動後も残す設定** — 帯域ON/OFF、モード、自分のchの変更は `data_dir/overrides.json` に原子的に書く。壊れていたら既定に戻して監視を続け、壊れたファイルは `overrides.broken.json` に残す。

- **ローカルAPIのbind先** — `api.host` は `127.0.0.1` 以外を設定の検証で拒む。
