## 無線・解析

- **chの書き方** — 設定では `"6g37"`・`"5g36"`・`"2g1"`・`"6GHz ch37"`・MHzの整数を受け付け、内部はすべてMHz。日本で使えないch（6GHzの偶数ch、5GHzのch149以上など）は読み込みで止める。
- **日本の5GHz** — W52/W53/W56の20ch（ch144を含む）。束ねられるのは40MHz（10本）、80MHz（36・52・100・116・132）、160MHz（36・100）。ch132〜144は80MHzまで。
- **自ブロック** — 自分のchを含む160MHzブロック。無ければ80→40→20MHz（予備chや自分のchが5GHzのch132〜144のとき）。
- **320MHzが2本候補になるch（ch33〜61）** — 局の範囲はEHT OperationのCCFS1で決める。束ね方の表から選ぶときは低い方（中心ch31）。
- **強さの合成** — アンテナごとの値（radiotapの2つ目以降の名前空間）があれば電力の和で合成し、無ければドライバが最初の名前空間に入れた値を使う。推測：iwlwifiの最初の値は2本の強い方で、和ではない（未確認）。
- **主chと幅の優先** — 幅はEHT Operation（情報あり）→ HE Operationの6GHz情報 → VHT Operation → HT Operation。6GHzのHE 6GHz情報で160MHzかつCCFS1=0のときは、CCFS0が160MHzブロックの中心なら160MHz、そうでなければ80MHzとみなす。IEが主chと矛盾したら20MHzとみなし「疑わしい」印を付ける。
- **Multiple BSSID（IE 71）の非送信BSS** — 今は展開しない（送信BSSだけ局の表に載る）。6GHzで1台が複数SSIDを出す場合、2つ目以降のSSIDは見えない。必要になったら追加する（提案）。

- **カーネル内の切り詰め（BPF）** — AF_PACKETのソケットにclassic BPFを付け、データフレームはMACヘッダの長さちょうど、制御フレームは16バイト、ビーコンとプローブ応答以外の管理フレームは32バイト（理由コードまで）に切り詰める。ペイロードはユーザ空間に来ない。そのため解析はFCSをヘッダの読みでは差し引かず、本文を読む管理フレームでだけ差し引く。
- **リトライ率の数え方** — 分母は「データフレームと、ビーコン以外の管理フレーム」。制御フレーム（Retryビットを持たない）とビーコン（再送されない）は除く。
- **自分のフレームを除く** — 自APのBSSIDと自端末のMAC（config の own.bssids・own.station_macs）を含むフレームは、活動量とリトライ率から除く。自リンクの状態は扱わない（仕様書）ため、他局の活動として数える。
- **IEの全部の解析は局ごとに5秒に1回** — それ以外のビーコンでは強さと時刻だけ更新する（処理能力のため）。
- **プローブ要求の本文（端末が探しているSSID）は読まない** — 端末の持つネットワーク名が分かってしまうため。端末の一覧はデータフレームのヘッダだけから作る。
- **統計の鍵は (主chのMHz, 受信の幅)** — 20MHzで受けたときと160MHzで受けたときは別に数え、基準も別に持つ（仕様書「chごとに数え、基準も同じ単位で持つ」）。

## 巡回（M2）

- **自ブロックの7秒を4つに分ける** — LIVEの10秒周期は「自ブロック1.75秒＋巡回3枠」を4回。自chから離れる時間は最大0.75秒（連続7秒＋3秒より短い）。切替の回数が増える分、実際の受信率は68.8%（割り当ては70%）。仕様書は配置を決めていないため。
- **外した帯域の枠の配り直し** — 1枠ずつ「ch数÷枠数（再訪の間隔）がいちばん長い組」に渡す。組のch数より多くは渡さない。渡す先が無ければ自ブロックの受信に戻す。自ブロック内の別chの枠と予備chの専用枠は動かさない。
- **QUIETの形** — 10秒周期で自ブロック内の別ch 4枠（1秒）、3周期（30秒）に1回だけ5GHzの生存確認を250ms。割り当ては89.2%、切替を除いた実測は88.0%。
- **予備chの専用枠** — 予備chが5GHz（自ブロック外）のとき、5GHzの3枠のうち1枠を専用にし、その予備chは5GHzの巡回の順番から外す。予備chを巡回から外した場合は専用枠も無くす（利用者の選択を優先）。
- **自ブロックのある帯域を外したとき** — 例えば6GHzを外しても自ブロック（160MHz）は見続け、それ以外の6GHzのchだけ巡回から外す（仕様書「自ブロックは外せない」）。自ブロックのchを個別に外す要求は断る。
- **生存確認の「周期」** — LIVEは10秒周期の2.4/5GHzの枠、QUIETと2.4/5GHzを両方外したときは30秒ごとの5GHzの生存確認、PREは1周。生存確認のchは、最近いちばん多く局が見えた5GHzのch（M3でつなぐ）。
- **初回起動の先回り** — 自ブロック（160MHz）、自ブロック内の別ch、自ブロック外のPSCを200msずつ（6GHz ch37なら12枠＝2.4秒）。
- **手動スキャンの順番** — 仕様書の優先の順（自ブロック → PSC → 6GHzのその他 → 5GHz → 2.4GHz）。既定の対象は巡回に入っているch、帯域やchを指定すれば巡回外も可。
- **PREと巡回外** — PREも巡回なので、外した帯域・chは見ない（自ブロックは見る）。2.4/5GHzを両方外したPREでは、30秒に1回5GHzの生存確認を挟む。
- **長い枠の区切り** — 自ブロックの1.75秒は0.5秒ずつ解析に渡す（画面と警報の更新を遅らせない）。同じ設定が続くときはtuneし直さない。
- **tuneに失敗したとき** — その枠の時間は待って次へ進む（空回りしない）。失敗の続きは受信停止の判定（M3）で扱う。

## 警報（M3）

- **警報のまとめ方（未決への仮定）** — 鍵は「種類:範囲」。割当違反2種はチームごと、新規参入は自分の帯域で1つ、正体不明の局は帯域ごと、署名は署名ごと、活動量とリトライ率は自chごと、同名SSIDはSSIDごと、deauthは自分で1つ、受信停止は1つ。同じ局に違う種類の警報が重なっても通知はまとめない（種類ごとに1通）。画面では局ごとに関係する警報を並べる（M5）。
- **通知のタイミング** — 発生（raised）は通知。当事者が最後に知らせたより増えたら「追加」を30秒以内でも通知。条件が10秒消えたら cleared（記録だけ）、解消の通知は「最後に発生・追加を知らせてから30秒」以降に出す。出す前に再び成り立てば、発生も解消も知らせない。これで同じ警報を30秒以内に重ねて知らせず、利用者が「解消した」と誤解する時間も作らない。
- **新規参入の基準** — 起動直後に見えた局は新規にしない：局の主ch（または受けたch）を0.15秒以上見たことがあってから現れた局だけを新規とする。10分以上見えなかった局が戻った場合と、自分の帯域の外から重なる位置にchを移した場合も新規。新規の扱いは10分（その間いて重なっている限り当事者）。自分の帯域＝自分のch×config の own.width。
- **局が「いる」とみなす時間** — 最後に見てから、そのchの再訪の間隔の2.5倍（最低60秒）。巡回外のchは600秒。
- **割当違反の対象** — チームが分かっている局（config・手動タグ・SSIDのパターン・RNR）だけ。予約ch＝割当ch＋予備ch。帯域の食い込みは、局の宣言した範囲が他チーム（自チームを含む）の予約chの20MHzにかかるとき。
- **正体不明の局を見る帯域** — 6GHzと、自分のch・予備chのある帯域。中央値は同じ帯域の他局（自APを除く）の強さ（指数移動平均）で計算。
- **RoboconFreeの6GHz出現** — 画面では成り立つ間「発生中」として出し、通知は署名ごとに一度だけ（再起動しても覚える。保存はM5）。
- **活動量の窓** — 今の値は直近の10秒の桶2つ（10〜20秒ぶん）で、受信が2秒以上あるとき。基準は過去10分の10秒の桶（受信0.5秒以上）の中央値で、桶が3つ以上あるときだけ判定。鍵は (自ch, 受信の幅) で、PREは20MHz、LIVE/QUIETは自ブロックの幅。
- **deauthのPMF** — 自APのビーコンのRSN（MFPR）→ config の own.pmf_required → 6GHzなら必須、の順で決める。
- **同名SSIDの別AP** — config の own.bssids が書かれているときだけ判定（無いとどれが本物か分からない）。自チームの判定もBSSIDが書かれていればBSSIDで行う。
- **受信停止の追加の条件** — 自ブロックへのtuneが3回続けて失敗したとき（6GHzが無効になった等）も同じ復旧の手順に入る。失敗（crit）のあとも5分ごとに復旧を試みる。周期の判定は、その周期の最後の生存確認の枠が終わった時点で行う。
- **PREの較正** — しきい値は自動で書き換えない。PREで約5分（1周以上）たったら、帯域ごとの局の数・強さの分布・強い局が重なるch・自chの活動量と、今のしきい値でどう判定されるかの説明を作り、画面に出す（人がconfigを直す判断に使う）。

## 通知（M4）

- **2026-10-14 ntfyへの送り方を確かめた** — `POST https://ntfy.sh/` にJSON（topic・message・title・priority・tags）で送る。ヘッダで送ると日本語の題名にRFC 2047の符号化が要るため、JSONにした。優先度は1（min）〜5（max）。（docs.ntfy.sh/publish）。ntfy.shの送信の回数制限はドキュメントに数字が無い → 429が来たら Retry-After を守って待つ。
- **通知の文面** — 題名は「緊急｜…」「警告｜…」「追加｜警告｜…」「解消｜…」。本文は警報の要約と時刻（JST）と「（ピットから見えたもの）」。Discordはcritだけで、`allowed_mentions` を空にして誰も呼び出さない。
- **再送の順番と間隔** — 宛先ごとに入れた順に送る（先頭が送れなければ後ろも待つ）。待つ間隔は2・4・8…秒、最大60秒（429はRetry-Afterまで）。crit・warn・解消は無期限。稼働中の通知は15分で捨て、新しいものに置き換える。
- **死活監視** — 1分ごとにGETで生存報告。失敗しても溜めない（死活監視は「届かないこと」で気づく仕組みのため）。
- **警報音** — critの発生と追加で `C`（0x43）を1バイト（`docs/buzzer.md`）。
- **http（https以外）の宛先** — ntfy・Discord・死活監視・中継のURLは https だけ。テストと開発のため、ループバック（127.0.0.1・localhost）の http だけ例外にした。

## 保存・ローカルAPI・画面（M5）

- **記録のラベルの「新しい方」** — 編集した側の時計の時刻で比べる（PCはPCの時計、アプリはアプリの時計）。スマホとPCはNTPで合っている前提。
- **イベントの記録先** — SQLiteの `events` 表と `data/events.jsonl` の両方。jsonlには警報と解消のほか、操作（モード、帯域ON/OFF、自ch、手動スキャン、タグ、ラベル、歩測、受信の見張り）も入れる。「発生を知らせない再発生」は記録しない（cleared と対で残っている）。
- **channels.csv** — 10秒ごとに57ch全部を1行ずつ（ts, freq, band, ch, state, 最後に受信してからの秒, 重なる局, 主chの局, 強い局, 最大の強さ, 活動量, 予約, 問題ch）。1日14時間で約28万行・約15MB。
- **CSVの書き出し** — 局ごとに1行。Excelで文字化けしないようBOM付きUTF-8。
- **手動のチーム名タグ** — SQLiteに残し、再起動後も効く。
- **ローカルAPIの守り** — Host・独自ヘッダに加え、Originヘッダがあれば自分以外の書き込みを断る。CSPは `default-src 'self'`（外部の資源・インラインのスクリプトとstyle属性は使わない。画面の動的なstyleはCSSOMで入れる）。`/docs` などの自動の説明ページは出さない。
- **画面の作り** — 外部のライブラリを使わない素のHTML・CSS・JavaScript（ピットのPCは回線が切れることがある）。1秒ごとに `/api/state` を取り、取れなければ前の表示を薄くして残し、上に「届きません」を出す。
- **画面の情報の階層（ユーザーの要望「一目で分かる」）** — 1) 上の帯：対処が要るか（「緊急 n」「警告 n」「検知なし」。安全とは書かない）、自ch、受信の状態、モード、見ていない範囲。2) 主役：6GHzのアナライザー（ch×強さ、局は宣言した帯域幅どおりの台形）。自分の帯域・受信中の160MHz・見ていないch（斜線）・強い局が3つ以上のch（黄の帯と「!」）・各chの「見ているか」と予約を同じ図に重ねる。5GHzと2.4GHzは小さく並べる。3) 右：発生中の警報（当事者を押すと局を選ぶ）、自chの活動量の推移、回避先の候補、PREの下見のまとめ。4) 下のタブ：局・端末・記録・イベント・巡回と手動スキャン・設定。局を選ぶと右から詳細が出て、図では他の局を薄くする。
- **局の色（2026-10-15 検証）** — 仕様書の「他高専＝黄、RoboconFreeとCineEye＝赤」に、自チーム＝青、所属不明＝紫、既知＝灰を足した。dataviz の validate_palette.js で明暗それぞれ合格（明：#2a78d6・#eda100・#d03b3b・#4a3aa7、暗：#3987e5・#c98500・#d03b3b・#9085e9）。明るい画面の黄は背景との比が3未満なので、記号（● ▲ ■ ◆ ○）と文字を必ず添え、表でも同じ情報を出す。
- **名前を付ける局を絞る** — 図に全部の名前は付けない。選んだ局 → 警報の当事者 → 自チーム → 新規 → 強い順に、重ならない範囲で最大14（5GHz・2.4GHzは5・4）。同じSSIDは1回だけ（RoboconFreeの乱立）。残りはホバーと表で読める。
- **ホバー** — 指した位置に一番近い局（台形の上の辺から14px以内）を拾う。無ければそのchの情報（見ているか、最後に受信してから、再訪の間隔、重なる局、活動量、予約）。

- **重なっているところのクリック（2026-10-15、ユーザーの要望）** — アナライザーで、ポインタの下にある局（台形の中か上の辺の近く）が2つ以上なら、ツールチップに「ここに重なる局 n」と全部を出し、クリックで全部の詳細を引き出しに並べる（上に強い順の一覧、下に1局ずつ）。重なる局はグラフでも全部強調する。タグ付けは「この局だけ開く」から（1局の画面で）。

- **機種推定：覚え帳と機種の表（2026-10-15、ユーザーが a＋b を選んだ）** — MACアドレスのネット検索はしない（MACから分かるのはOUIのメーカーだけで、PCの中の ieee-data と同じ。見えた他人の機器のMACを外に出さない）。代わりに次の2つ。どちらも見えた局の情報は外に送らない。
  - 指紋（`model_fp`、10桁）：IEの並び（TIM・チャネル切替の告知・Quiet・BSS Load を除く）と、HT/VHT/HE/EHT・HE 6GHz・拡張能力のバイト列（HTの40MHz可否とSMパワーセーブのビットは設定で変わるので除く）のSHA-1。SSID・BSSID・chには左右されない。機種ごとに必ず違うとは限らない（同じチップ・同じファームウェア）ので、画面に「同じ指紋の局 n」を出し、2局以上に効くときは覚える前に確かめる。
  - 覚え帳（a）：局の詳細の「機種を覚える」で、指紋に機種の名前を覚える（`data_dir/model_book.json`、デスクトップの画面だけ。アプリと中継からは変えられない）。同じ指紋の局にも出る。設定のタブで一覧・忘れる・表の形で書き出す。

## 実機の層（M7）

- **特権の分け方** — 無線の操作（iw・ip・modprobe・AF_PACKET）は小さな補助プロセス radiod（root）だけが行い、本体（解析・API・中継・通知）は普通のユーザーで動かす。間はUnixソケット（`/run/wifiwatch/radiod.sock`、0660、グループ wifiwatch、許すuidも指定できる）。radiod が受ける操作は決まったもの（tune・capture・survey・復旧の手順・hello）だけで、値はradiodでも検査する。pm2は root で動かし、本体は `uid` で普通のユーザーに落とす（仕様書「sudo pm2」）。
- **tuneの書き方** — `iw dev <IF> set freq <主ch> <幅> <中心>` を先に試し、通らなければ `HT20`/`NOHT`/`HT40±`/`<幅>MHz` の書き方を試す。通った書き方を幅ごとに覚える（iwの版で受け付けが違うため。実機の確認6で確かめる）。
- **受信したchの確かめ** — radiotapのchが合わせたchと違うフレームは捨てる（切替の前後に紛れたもの）。tuneの直後にソケットに溜まったものは読み捨てる。
- **起動時の手順** — radiod は起動時に、合否ゲートと同じく「管理モードでスキャン → 国設定の確認 → モニタ」を行う。
- **合否ゲートが不合格のときの代わり** — 管理モードのパッシブスキャン（`iw dev <IF> scan passive`）。スキャン結果は `iw` の文字の出力ではなく、nl80211（generic netlink）から生のIEで受け取り、解析部にビーコンとして渡す（局の一覧・帯域幅・割当違反・署名がそのまま動く）。開発PCで、nl80211の読み取りが本物のカーネルで動くことを確かめた（読み取りだけ・sudoなし、2026-10-15）。画面には「見ていない：活動量・リトライ率・deauth・160MHz受信（スキャンだけのモード）」と出す。
- **実機の確認の道具** — `wifiwatch.hwprobe`（frames・switch・survey・eht・reload-check・bench・own-rssi）。数えて要約を出すだけで、フレームは保存しない。
- **自APの強さの記録** — ピットとフィールドの差（約9dB）を実測できるよう、`own.bssids` の局の強さを10秒ごとに `data/own.csv` に残す（仕様書「実機で確かめる」のため）。
- **指示が届くまでの秒** — PCがアプリの指示を受け取ったとき、中継が受け付けてからの秒（中継の時計どうし）をイベントに残す（実機の確認12のため）。
- **NetworkManager** — `/etc/NetworkManager/conf.d/99-wifiwatch-unmanaged.conf` で監視のIFだけ管理外にする（`setup.sh` が確認してから書く）。

- **スキャンだけのモードは能動スキャンに切り替えない（2026-10-15）** — パッシブスキャン（`iw scan passive`）が失敗（busy など）したとき、前は `iw scan`（プローブ要求を送る）でやり直していた。受信専用の約束に反するので、パッシブだけにし、失敗したら5秒ほどでやり直す。
- **受けられないchは「見ていない」** — スキャンだけのモードで、無線が受けられないch（`iw phy <phy> info` で disabled か一覧に無いもの）は、受信していた秒を0として返す。解析部も、受信していた秒が0の枠ではそのchを「見た」にしない。radiod は受けられないchを hello で返し、画面とアプリの「見ていない」に「この無線では受けられない」と出す（状態の写しには、あるときだけ `bands.unreceivable` を付ける）。AX210で6GHzが無効になったときも同じ扱いになる。
- **ドライバの読み込み直しは iwlwifi のIFだけ** — `/sys/class/net/<if>/device/driver` が iwlwifi でなければ断る（開発PCの無線のドライバに触らない、関係のないモジュールを読み込まない）。
- **開発PCで本物を見る** — ユーザーの希望（2026-10-15）「本番とできるだけコードを変えずに」「動いている間はアナライザーが最優先、通信は切れてよい」。本番と同じモニタモード（radiod ＋ 本体）で動かし、開発PCの手順は `tools/devpc_monitor.sh`（NetworkManagerから外す → radiod → 本体、Ctrl-Cで戻す）にまとめた。通信を切りたくないときは本番の「スキャンだけのモード」。手順は `HARDWARE_TEST.md` の「0'」。開発PCの無線（RTL8852BE、rtw89）は nl80211 で monitor に対応、chは2.4GHz 14・5GHz 25（disabled 3）、6GHzは一覧に無い（2026-10-15、sudoなしで確かめた）。
- **無線にないchには合わせない** — モニタモード（LinuxRadio）でも、`iw phy <phy> info` に載っていないch（ハードウェアに無い。6GHz非対応の無線の6GHz）は、`iw set freq` を呼ばず、失敗にもせず、受信していた秒0で返す（受信停止の誤検知と復旧の空回りを防ぐ）。disabled（国設定で使えない）は載っているので、従来どおり合わせて失敗させ、復旧に回す（AX210の6GHzが無効になったとき）。radiod は起動時にこの一覧を読む。
- **管理モードのスキャンもパッシブ** — radiod の起動時・復旧時の `managed_scan` と `deploy/gate.sh` のスキャンを `iw scan passive` にした（受信専用。国情報はビーコンから受ける）。

## アプリ（M8）

- **2026-10-15 Androidの確かめ（SDKのソースと api-versions.xml）** — `ScanResult.getInformationElements()` と `ScanResult.InformationElement`（getId・getIdExt・getBytes）はAPI 30から。拡張IE（id=255）の中身は拡張IDを除いたもの。`getWifiStandard()` はAPI 30、`CHANNEL_WIDTH_320MHZ`・`WIFI_STANDARD_11BE`・`getWifiSsid()` はAPI 33。`WifiManager.startScan()` はAPI 28で非推奨（使える）。`getScanResults()` は ACCESS_FINE_LOCATION と ACCESS_WIFI_STATE が要り、位置情報サービスがオンであること。スキャンは前面で2分に4回まで（開発者オプションで解除できる。developer.android.com の Wi-Fi scanning）。`ConnectivityManager.requestNetwork(NetworkRequest, NetworkCallback)` は CHANGE_NETWORK_STATE が要り、unregister するまで続く。`Network.getSocketFactory()`・`Network.getAllByName()` はAPI 21から。Android はマルチBSSIDの非送信BSSも別の結果として返す（11ax以上）。
- **版の組み合わせ** — ユーザーの環境で動いている組み合わせに合わせた：Gradle 9.4.1、AGP 9.2.1（Kotlinは内蔵）、Kotlin 2.2.10（Composeのプラグイン）、Compose BOM 2026.02.01、KSP 2.3.12、Room 2.8.5、WorkManager 2.11.0、OkHttp 4.12.0、lifecycle 2.9.4。compileSdk・targetSdk 36、minSdk 30。
- **モバイル回線への固定** — `requestNetwork(TRANSPORT_CELLULAR＋NET_CAPABILITY_INTERNET)` で得たNetworkに、OkHttpのソケット（`socketFactory`）と名前解決（`dns` に `Network.getAllByName`）の両方を結びつける。`bindProcessToNetwork` は使わない（操縦用アプリやWebViewに影響しないよう、wifiwatchの通信だけを結びつける）。WorkManagerの再送も同じクライアントを使う（「ネットワークあり」の条件だけに頼らない）。設定に「固定する」のスイッチ（既定オン）を置き、オフはモバイル回線のない端末で試すときだけ。
- **指示は待ち行列に入れない** — 手動スキャンと帯域ON/OFFはその場で送り、20秒だけ送り直す。届かなければ「送れなかった」と出す（WorkManagerで後から送ると、回線が戻ったあとで古い手動スキャンが走りうるため）。ラベルの変更と歩測の記録は待ち行列（Room）に入れ、WorkManagerで無期限に送り直す。要求IDつきなので二重に届いても結果は同じ。
- **トークンの保存** — Android KeystoreのAES-256-GCMの鍵で暗号化してSharedPreferencesに置く（`security-crypto` の EncryptedSharedPreferences は非推奨のため使わない）。
- **平文のhttp** — ネットワークのセキュリティ設定で、10.0.2.2・127.0.0.1・localhost だけ許す（エミュレータからローカルの中継へ）。本番は https。
- **歩測の記録** — 1地点で何回もスキャンして局ごとにまとめ、強さは中央値。IEは生のバイト列（`ies_hex`）で残す（PCでも同じ解析ができるように）。IEが無い局は ScanResult の channelWidth と centerFreq0 で幅を決める。30秒より古い結果（前のスキャンの残り）は使わない。
- **画面** — 下のタブで「状態・スキャン・帯域・記録・歩測」、設定は右上。状態の画面の一番上に判定（緊急／警告／検知なし／PCから応答なし）。状態の写しが30秒より古ければ「検知なし」ではなく「PCから応答なし」と出す。chの帯（6/5/2.4GHz）はデスクトップと同じ意味の色と斜線。アイコンの部品（material-icons）は使わず、記号の文字で済ませた（依存を増やさない）。

- **エミュレータ（2026-10-15、ユーザーの許可を得て入れた）** — cmdline-tools 16111833、system image android-36 google_apis x86_64、AVD `wifiwatch36`（pixel_8a）。エミュレータには模擬のWi-Fi（AndroidWifi、既定の回線）と模擬のLTE（eth0）の両方があり、どちらからも 10.0.2.2（開発PC）に届く。そこで固定はオンのまま確かめた：`adb shell svc data disable` でモバイルデータだけ切ると、Wi-Fiが生きていても「モバイル回線が使えません」になり、Wi-Fiには流れない。
- **デバッグ版だけの起動引数** — `relay_url`・`token`・`pin_cellular` を `adb shell am start --es ...` で入れられる（エミュレータでの通しの確認のため。`BuildConfig.DEBUG` でないときは何もしない）。トークンの長さとURLの検査は設定の画面と同じ。
- **古い状態の出し方** — 状態の写しが30秒より古いとき、端末が中継に届かない（回線の問題）なら「中継に届かない」、中継には届くがPCが状態を置いていないなら「PCから応答なし」と分けて出す（直す場所が違う）。その下の状態は薄くし、「以下は◯秒前の状態です」と添える。「◯秒前」は1秒ごとに進める（届かない間も止まらない）。
- **見ていないchの点** — chの帯で、巡回外・手動スキャン中などのchに出る「強い局」の点は、前に見えた局（いまの様子ではない）なので白抜きにする。見ていないところの一覧は、警報より上に出す。
- **ラベルの「反映待ち」** — 記録の画面はRoomの写しを見張り、反映待ちの間だけ5秒ごとに一覧の写しを読み直す（最大2分。1回は中継のRedisコマンド2つなので、1回の保存で最大48コマンド）。PCの正本に入ったら消える。
- **手動スキャンの完了から記録へ** — 完了した指示のカードに「記録を開く」を置く。まだ一覧を読んでいない記録は、中継が本体に付けて返す一覧用の情報（`meta`）を使う。
- **溜まりの送り直しを早める** — ラベル・歩測の再送は WorkManager の指数的な間隔（15秒から倍、上限5時間）だが、アプリの問い合わせが失敗から成功に変わったときと開いた直後は、待ちを捨ててすぐ送り直す（`ExistingWorkPolicy.REPLACE`）。送っている途中を取り消しても要求IDで冪等。
- **選んでいるチップに ✓** — 色だけに頼らない（FilterChipの選択に ✓ を付ける）。巡回外のchは灰色に加えて打ち消し線。

## 偽の無線のモデル（実機で確かめるまでの仮定）

- 受信機は主20MHzで検出する。20MHzのビーコンは局の主chでだけ聞こえる。重複ビーコンの局は局の帯域内のどの20MHzでも聞こえる。
- データは局の全幅で送る。受信機の主20MHzが局の範囲内で、局の範囲が受信の幅に収まるときだけ聞こえる（160MHz受信で他局の160MHz送信が受信できる、は未検証の仮定）。320MHzのデータは聞こえない。
- ACKは局の帯域に重複して送る。
- 切替に30ms、感度-91dBm。

## 設定

- **再起動後も残す設定** — 帯域ON/OFF、モード、自分のchの変更は `data_dir/overrides.json` に原子的に書く。壊れていたら既定に戻して監視を続け、壊れたファイルは `overrides.broken.json` に残す。
- **ntfyのトピック** — 公開トピックなので16文字以上の英数字を必須にした（仕様書「推測されにくい文字列」）。
- **ローカルAPIのbind先** — `api.host` は `127.0.0.1` 以外を設定の検証で拒む。
