# wifiwatch 実装の依頼（Claude Code 向け）

このリポジトリで、NHK高専ロボコン全国大会向けのWi-Fi監視システム「wifiwatch」を実装してください。部品は3つです：ピットに置くPC側、自作のAndroidアプリ、その2つをつなぐ中継（Vercel＋Upstash Redis）。振る舞いは仕様書が正です。このファイルには、実装の方針と進め方を書きます。

```
アプリ ──モバイル回線──▶ 中継（Vercel＋Upstash） ◀──テザリング回線（PCから問い合わせ）── PC
                                                       PC ──▶ ntfy・Discord（中継を通さない）
```

## 1. 資料と優先順位

- `docs/spec.md`：仕様書「wifiwatch 仕様（全国大会向け）」をMarkdownで書き出したもの。振る舞い・数値・警報の条件・画面の要件は、すべてここが正。図は書き出しで抜けることがあるが、同じ内容は本文にある。
- このファイル：構成、技術の選び方、進め方、守ること。
- 食い違ったら仕様書を優先する。仕様書で「暫定」「未決」「未確認」となっている点は、仮定を置いて進め、`docs/DECISIONS.md` に「何を・なぜ・どう仮定したか」を1行ずつ残す。
- Vercel・Upstash・Androidの制限とAPIは変わりやすい。使う前に現行のドキュメントで確かめ、確かめた日付と中身を `DECISIONS.md` に残す。このファイルに書いた名前と数値も、確かめるまでは案として扱う。
- 質問で作業を止めない。ただし次の2つだけは、先に私に聞く。
  - 不可逆な操作と、外に出る操作（削除、force push、sudo、ネットワークや権限の設定変更、Vercelへのデプロイ、外部サービスのアカウント・課金・環境変数の操作）
  - 読み違えると全部やり直しになる分岐
- 以前のv1コード（USBアダプタ2本が前提）は使わなくてよい。

## 2. 最初にやること

1. `docs/spec.md` を最後まで読む。
2. 開発環境を確かめる（Ubuntuの版、Python、Node.jsとnpm、Android SDKとJDKの有無）。足りないものは入れ方を私に示す。自分で `sudo apt` はしない。
3. リポジトリ直下に `CLAUDE.md` を作り、3章「守ること」を書き写す。
4. `docs/PLAN.md` に、6章のマイルストーンを作業単位に分けた計画を書く。
5. M0から順に進める。マイルストーンが終わるたびに `docs/PROGRESS.md` に追記し、gitにコミットして、短く報告する。pushは私が言うまでしない。
6. 途中で私が新しいセッションに切り替えることがある（特にM8のアプリから）。`CLAUDE.md` と `docs/PROGRESS.md` を読めば続きから始められる状態を、常に保つ。

## 3. 守ること（CLAUDE.md に書き写す）

- 受信専用。AX210から送信・パケット注入・deauthをしない。管理モードに戻すのは、合否ゲートと復旧のときのスキャンだけ。
- データフレームはMACヘッダまでしか見ない。ペイロードは読まない・保存しない。pcapを保存しない。
- chは周波数（MHz）で持つ。ch番号は帯域をまたいで衝突する（2.4GHzのch1は2412MHz、6GHzのch1は5955MHz）。
- 6GHzの局の主chは、受信した周波数ではなく、HE Operationに書かれた主chで決める（重複ビーコンは主ch以外でも届く）。
- 活動量やフレーム数は「そのchを実際に受信していた秒数」で割る。時計の秒で割らない。
- 「検知なし」と「見ていない」（巡回外、手動スキャン中、受信停止中）を、データでも、デスクトップの画面でも、アプリでも区別する。
- PCは外からの接続を受けない。PCのAPIと画面は `127.0.0.1` にだけbindする（`0.0.0.0`、テザリングのIFにはbindしない）。ポートを開けない。VPNやトンネルを入れない。遠隔の操作は、PCから中継への外向きの問い合わせだけで行う。
- ローカルAPIは、Hostヘッダが `127.0.0.1` か `localhost` の要求だけ受ける。書き込みは独自ヘッダ（例：`X-Wifiwatch: 1`）付きの要求だけ受ける。ブラウザを経由したなりすまし（DNS rebinding、CSRF）を防ぐため。
- 中継のAPIは、読み出しも含めてトークン必須。トークンはアプリ用とPC用に分け、アプリ用のトークンではPC側のAPIを使えない。トークンの検査はRedisに触る前に行う（無料枠を他人に使わせない）。
- 中継が受ける指示は、手動スキャンと帯域ON/OFFだけ。モードの切替、設定の書き換え、任意のコマンドは受けない。値は中継とPCの両方で検査する。
- 指示の期限は60秒。中継は期限を過ぎた指示をPCに渡さない。PCも、受け取った時点で期限を過ぎていれば実行しない。
- 中継はWebSocketや常時接続を使わない。1回の問い合わせで使うRedisのコマンド数は、4.2の上限を超えない（無料枠を守るため）。
- 通知（ntfy・Discord）は中継を通さない。中継が止まっても、PCの監視と通知は止めない。
- subprocessに渡すのは、検証した周波数・幅・IF名だけ（`shell=True` は使わない）。
- 時刻はUTCで保存し、表示はJST。
- sudoが要るコマンドと、NICの状態を変えるコマンド（`ip link set ... down`、`iw ... set type monitor` など）は、実行する前に必ず私に確認する。作業中のPCのWi-Fiが切れるため。
- 秘密情報（アプリ用とPC用のトークン、Upstashの接続情報、ntfyのトピック、Discord Webhook、死活監視のURL）はコミットしない。中継の秘密はVercelの環境変数に置く。コミットするのは `config.example.json` と `relay/.env.example` だけ。

## 4. 構成

```
server/    PC側（Python）
relay/     中継（TypeScript、Vercel Functions ＋ Upstash Redis）
android/   自作アプリ（Kotlin）
deploy/    合否ゲートとセットアップのスクリプト、pm2の設定
docs/      spec.md, PLAN.md, DECISIONS.md, PROGRESS.md, api.md, relay.md, HARDWARE_TEST.md
testdata/  合成フレームとIEの試験データ、中継とのやりとりの見本（PC側・中継・アプリで共用）
```

### 4.1 PC側（server/）

- Python（Ubuntu標準の3.10以上）、venv、依存の版は固定する。HTTPはFastAPI＋uvicorn、保存はSQLite。別のものにする場合は、理由を `DECISIONS.md` へ。
- モジュールの分け方（名前は任せる）：
  - **radio**：IFのモード・周波数・幅の切替、合否ゲート、生存確認と復旧（管理モードでスキャン → 国設定がJPで6GHzが有効かを確認 → モニタ）。実機用と、テスト用の偽物（合成フレームを流す）を、同じインタフェースで作る。
  - **capture**：radiotap、802.11ヘッダ、IE（HE/EHT Operation、RNR、RSN、WPS、ベンダIE）の解析。RSSIは2本を合成した値を使う。
  - **scheduler**：PRE/LIVE/QUIET、巡回の枠の割り当て、手動スキャン、帯域ON/OFF。
  - **analyzer**：局の表、chごとの統計、警報（仕様書「検知と警報」の表の全部）。
  - **classify**：`signatures.json`、チーム対応表、OUI、機種推定、RNRによる紐付け。
  - **notify**：ntfyとDiscord、抑制と追加通知、無期限の再送（再起動しても消えない待ち行列）、稼働中通知、死活監視へのping、ピットの警報音。
  - **store**：記録・ラベル・イベントのSQLite、`events.jsonl`、`channels.csv`、JSON/CSVの書き出し。中継に送る前の待ち行列もここに持つ（再起動しても消えない）。
  - **api**：ローカルAPI（127.0.0.1だけ）と、デスクトップの画面（ダッシュボード）の静的ファイル。
  - **relay_client**：中継への問い合わせ（4.2、4.4）。受信と解析の処理を止めないよう、別スレッドか非同期で動かす。
    - 間隔：アプリが前面にいないとき10秒、いるとき2秒（設定で変えられる）。起動直後は版数なしで問い合わせ、受信箱を全部受け取る（落ちる前の取りこぼしを拾う）。
    - 受け取った指示は、ローカルAPIと同じ内部の関数で実行する（中継専用の実行経路を作らない）。受け取り・実行中・結果を、状態の写しに載せる。
    - アプリが前面にいる間だけ、状態の写しを問い合わせと同じ要求で置く。
    - 新しい記録と、PCで変えたラベルを中継に置く。中継から、アプリで変えたラベルと歩測の記録を取り込む。PCが正本で、ラベルは編集時刻の新しい方を残す。
    - 中継につながらないときは溜めて、つながったら送る。
- 時刻を外から注入できる作りにする。巡回と警報と中継の問い合わせを、実時間を待たずにテストするため。
- 処理能力：160MHz受信中の大量のフレームを取りこぼさないこと。目安として、毎秒5000フレームを1コアで処理できるかを測る（目安の値は未確認）。足りなければscapyをやめ、軽い自前の解析にする。測った数字は `PROGRESS.md` へ。
- 権限：受信とIFの操作に要る部分だけが特権を持つ形にできるなら、そうする（APIと relay_client をrootで動かさない。方針は `DECISIONS.md` へ）。
- 設定：`config.json` を起動時に検証し、間違いは分かる言葉で止める。中継のURLとPC用のトークンもここに置く。帯域ON/OFFなど画面やアプリから変えた設定は、別に保存して再起動後も残す。
- 警報音：USBシリアルで1バイト送ると鳴る相手を想定する（相手はSTM32＋ブザー。ファームは対象外で、送る内容だけ `docs/` に書く）。

### 4.2 中継（relay/）

- TypeScript、Vercel Functions（Node.jsランタイム）。フレームワークは使わず、`api/` にWeb標準のRequest/Responseで書く。保存はUpstash Redis（`@upstash/redis`、RESTで呼ぶ）。別のものにする場合は、理由を `DECISIONS.md` へ。Node.jsの版はVercelが対応する版に合わせる。
- 関数のリージョンは東京にする（`vercel.json` の `"regions": ["hnd1"]`。Hobbyでも1リージョンなら選べる）。既定のiad1のままだと、問い合わせのたびに太平洋を往復する。
- 中身は、Redisを引数で受け取る関数として書く。`api/` はそれを呼ぶだけの薄い層にする。テストでは、同じインタフェースのメモリ上の偽物を渡す。偽物は、コマンド数と転送したバイト数を数える。
- ローカルで動かす小さなHTTPサーバ（同じ関数と偽物のRedisを使う）を用意し、PC側とエミュレータのアプリからの通しに使う。`vercel dev` もVercelへのログインもなしで、全部テストできる形にする。
- Redisの持ち方（キーの名前は任せる）：
  - **版数**：アプリが指示・ラベルの変更・歩測の記録を置いたとき、またはアプリを開いたときに1増やす。PCは「前回と違うか」で比べる（大小では比べない。Redisが空に戻っても取りこぼさないため）。
  - **前面の印**：アプリが前面にいる間だけある印。期限付き（約10秒）で、アプリの問い合わせのたびに延ばす。
  - **受信箱**：PCがまだ受け取っていない指示・ラベルの変更・歩測の記録。PCが「保存した」と返すまで消さない（受け取った直後にPCが落ちても失わない）。指示には中継の時計で受付時刻を付け、60秒を過ぎたものはPCに渡さずに消す。
  - **状態の写し**：PCが置く。1回8KB以下（帯域の見込みの前提）。消さずに上書きし、中継が受け取った時刻を付ける。アプリはその時刻からの経過を出す。経過は中継の時計どうしで比べ、スマホやPCの時計のずれを持ち込まない。
  - **記録の写し**：1件ずつ置き、一覧用の索引を持つ。合計の上限（例：100MB）を超えたら古い順に消す（PCが正本なので、消えても困らない）。
- 1回の問い合わせで使うRedisのコマンド数の上限：
  - PCの待機中（アプリが前面にいない）：1。版数（と前面の印）を1コマンドで読み、版数が前回と同じならそれで返す。
  - PCのアプリ前面中：4（読む1、状態の写し1、受信箱の取り出しと片付け2）。
  - アプリの2秒ごとの問い合わせ：2（前面の印を延ばす1、状態の写しを読む1）。
  - 指示・ラベル・記録を置く操作は回数が少ないので、1回5コマンド以内を目安にする。
- 無料枠の見込み（仕様書「経路と安全」）は、この上限が前提。大会4日でUpstashのコマンドが約29%、30日つけっぱなしで約52%、帯域が約4%。
- 中継が断るもの：トークンがない・違う要求、決まっていない種類の指示、範囲外の値（帯域・ch）、PCがまだ受け取っていない手動スキャンがあるときの次の手動スキャン、大きすぎる本文。
- `docs/relay.md` に、キーの設計、APIの確定版、デプロイの手順（Vercelのプロジェクト、Upstashの接続、環境変数、リージョン）を書く。環境変数の名前は、VercelのMarketplaceでUpstashをつないだときに入るものを、現行のドキュメントで確かめる。デプロイごとに作られるURLにはVercelの保護（Deployment Protection）がかかることがあるので、アプリとPCに設定するのは本番のドメインにし、保護の設定も確かめる。

### 4.3 自作アプリ（android/）

- Kotlin、Jetpack Compose、Room、WorkManager。minSdkは30（ScanResultのIEを読むため）。主な端末はPixel 9a/8a。
- 通信の相手は中継だけ。PCには直接つながない。
- 通信はモバイル回線に固定する。`ConnectivityManager.requestNetwork`（`TRANSPORT_CELLULAR`、`NET_CAPABILITY_INTERNET`）で得たNetworkに、HTTPクライアントのソケットと名前解決の両方を結びつける。ロボットのWi-Fi（インターネットなし）には流さない。VPNは使わない。WorkManagerの再送も同じくモバイル回線で行う（制約の「ネットワークあり」だけに頼らない）。具体のAPIは現行のAndroidのドキュメントで確かめる。
- 前面にいる間だけ、2秒ごとに状態を取る。背面では取らない（溜めた送信の再送は除く）。開いたときは中継に「開いた」と伝える。これで版数が上がり、PCが10秒以内に気づいて2秒間隔に入る。
- 画面：
  1. **状態**：PCのモード、巡回中の帯域（巡回外は灰色）、発生中の警報、状態の写しの古さ（古ければ「PCから応答なし」）。
  2. **手動スキャン**：帯域・chを選んで指示し、「送った → PCが受け取った → 実行中（残り秒数）→ 完了」を出す。60秒たってもPCが受け取らなければ「PCに届かなかった」。QUIET中は確認を出す。確認なしの指示をPCが断ったときも、確認を出して送り直せる。
  3. **帯域ON/OFF**：帯域とchごとのスイッチ。自ブロックは外せないことが分かる表示にする。PCに反映されるまでは「反映待ち」と出す。
  4. **記録**：中継の写しから、一覧（種類・日時・場所・帯域で絞り込み）、詳細（局の表とchごとのグラフ）、ラベル編集（場所・タグ・メモ）。
  5. **歩測**：スキャン → 場所ラベル → 保存 → 中継に送る。届かなければ端末に溜めて、あとで送る。JSONの書き出しもできる。
  6. **設定**：中継のURL、アプリ用のトークン（暗号化して保存）、場所ラベルの選択肢。
- Wi-Fiスキャンの権限と制限は、Androidの現行のドキュメントで確かめてから実装する（スキャン回数の制限は、開発者オプションで解除済み）。
- ScanResultから、SSID・BSSID・周波数・帯域幅・中心周波数・RSSI・規格・IE（取れれば）を記録する。IEからHE/EHT Operationを読んで、主chと帯域幅を出す。解析の正しさは `testdata/` の共通データで、PC側と同じ答えになることを確かめる。
- 送信とラベルの変更は、失敗したらWorkManagerで再送する。要求ごとにIDを付け、二重に届いても結果が変わらないようにする。

### 4.4 API（案。確定版は `docs/api.md` と `docs/relay.md` に書く）

PCのローカルAPI（127.0.0.1だけ。デスクトップの画面が使う）：

| メソッドとパス | 中身 |
| --- | --- |
| `GET /api/state` | モード、巡回中の帯域、chごとの占有、発生中の警報、手動スキャン中か、中継との最後の問い合わせが通った時刻 |
| `POST /api/scan` | 手動スキャンの指示（対象の帯域・ch）→ スキャンID。実行中なら409。QUIET中は `confirm: true` がなければ断る |
| `GET /api/scan/{id}` | 進み具合と結果 |
| `GET /api/bands`、`PUT /api/bands` | 帯域とchのON/OFF。自ブロックを外す要求は断る |
| `GET /api/records`、`GET /api/records/{id}` | 記録の一覧と詳細（絞り込みあり） |
| `PATCH /api/records/{id}` | ラベルの変更 |
| `GET /api/records/export` | JSON/CSVの書き出し |
| `POST /api/mode` | モードの切替（デスクトップだけ。中継からは受けない） |

中継のAPI・アプリ用（アプリ用のトークン）：

| メソッドとパス | 中身 |
| --- | --- |
| `POST /api/app/poll` | 前面の印を延ばし（開いた直後は版数も上げる）、状態の写しと、中継がそれを受け取った時刻を返す。2秒ごと |
| `POST /api/app/commands` | 指示（`scan` か `bands`）を置く。要求IDで冪等 → 指示ID |
| `GET /api/app/records`、`GET /api/app/records/{id}` | 記録の写しの一覧と詳細 |
| `PATCH /api/app/records/{id}` | ラベルの変更（編集時刻つき） |
| `POST /api/app/records` | 歩測の記録。要求IDで冪等 |

中継のAPI・PC用（PC用のトークン）：

| メソッドとパス | 中身 |
| --- | --- |
| `POST /api/pc/sync` | 前回の版数を送る。変化がなければRedis 1コマンドで返す。変化があれば、受信箱の中身（期限内の指示、ラベルの変更、歩測の記録）と前面の印を返す。状態の写し（アプリが前面にいる間だけ）と「保存した」の知らせは、同じ要求に載せる |
| `PUT /api/pc/records/{id}` | 記録の写しを置く。ラベルの更新もこれで送る |

書き込みは、どれも要求IDで冪等にする。

## 5. ハードを使わない開発

- 実機の層以外は、ハードなしで全部テストできる作りにする（偽の無線、合成フレーム、時刻の注入、偽のRedis、ローカルの中継）。
- 合成フレームの生成器を作り、結果を `testdata/` に置く。最低限、次を含める：
  - 2.4/5/6GHzのビーコン
  - 6GHzのHE Operation（20/40/80/160MHz）とEHT Operation（320MHz）
  - 重複ビーコン、RNR、deauth、リトライ付きのデータフレーム、FCS付きのフレーム
- 中継とのやりとりの見本（指示、状態の写し、記録の写し、ラベルの変更）を `testdata/` に置き、PC側・中継・アプリのテストで共用する。
- 実機でしか確かめられないものは、`docs/HARDWARE_TEST.md` に手順と合否の基準を書く。実機のコマンドは私が実行する。
  - 6GHzのモニタ、160MHz受信、`survey dump`、iwlwifiの読み込み直しで6GHzが消えるか
  - アプリの指示が、中継とテザリング回線を通ってPCに何秒で届くか
  - ロボットのWi-Fiにつないだまま、アプリがモバイル回線で中継に届くか（操縦用アプリと同時に動かす）

## 6. マイルストーン（この順に進め、完了条件を満たしたら次へ）

- **M0 土台**：リポジトリ、`CLAUDE.md`、`config.example.json` とその検証、偽の無線、合成フレームの生成器、`relay/` の雛形（ビルドとテストが通る）。
- **M1 解析**：radiotap・ヘッダ・IEの解析、局の表、chごとの統計。
  - 完了条件：6GHzのビーコンが局の表に載り、主chと帯域幅（160/320MHzを含む）が正しい。重複ビーコンを主chで数える。
- **M2 巡回**：PRE/LIVE/QUIET、枠の割り当て、手動スキャン、帯域ON/OFF。
  - 完了条件（仕様書の表と照合）：LIVEで自chの受信率70%。再訪の間隔の最大が、自ブロック内の別ch 約20秒、6GHzのその他 40秒、5GHz 約70秒、2.4GHz 130秒。QUIETの自ch受信率が約89%。PREの1周が約14秒。手動スキャンが全57chで約14秒、6GHzだけで約6秒。帯域を外すと枠が配り直され、自ブロック内の別chの4枠と生存確認は残る。
- **M3 警報**：仕様書の表の全警報と、生存確認・復旧。
  - 完了条件：警報ごとに「鳴るべき場面」と「鳴ってはいけない場面」のテストがある。静かな6GHzで受信停止が鳴らない。PREからLIVEへの切替で、活動量の警報が鳴らない。
- **M4 通知**：ntfy・Discord、抑制、無期限の再送、稼働中通知、死活監視、警報音。
  - 完了条件：偽のHTTPサーバを使い、回線が切れても警報が失われず、戻ったら届くことを確かめる。
- **M5 保存・ローカルAPI・画面**：SQLite、ローカルAPI、ダッシュボード（グラフの1秒更新、再読込で即表示、初回は約5秒、手動スキャン、帯域ON/OFF、記録とラベル、巡回外の灰色表示）。
  - 完了条件：偽の無線で起動し、ブラウザから全部の操作ができる。Hostヘッダと独自ヘッダの検査を、断る場面と通す場面の両方でテストする。
- **M6 中継**：`relay/` と、PC側の relay_client。
  - 完了条件：
    - ローカルの中継（偽のRedis）を挟んで、テスト用のアプリ役 → 中継 → 偽の無線で動くPC → 中継 → アプリ役、の往復が通る（手動スキャン、帯域ON/OFF、記録の閲覧、ラベル、歩測の記録）。
    - 4.2のコマンド数の上限を、テストで固定する。
    - 偽のRedisが数えたコマンド数と転送量から、仕様書の2つの場面（大会4日：1日14時間稼働でアプリは3時間、30日つけっぱなし）の月の使用量を出す。仕様書の見込み（コマンド約29%と約52%、帯域約4%）を超えないことを確かめ、数字を `PROGRESS.md` へ。
    - トークンなし、違うトークン、アプリ用のトークンでPC側を使う要求が断られ、どれもRedisのコマンドを1つも使わない。
    - 60秒を過ぎた指示がPCに渡らない。同じ要求IDを二重に送っても結果が変わらない。PCが受け取ってから保存するまでに落ちても、何も失わない（期限内の指示は、再起動後にもう一度届く）。
    - 中継につながらない間も、監視と通知（偽のntfy・Discord）が止まらない。つながったら、溜めたものが送られる。
  - `docs/relay.md` を書く。デプロイは私が行うか、私の確認を取ってから行う。
- **M7 実機の層**：iwとipの操作、合否ゲート、セットアップ、pm2の設定、`HARDWARE_TEST.md`。
  - 完了条件：私が実機で、手順どおりに動かせる。
- **M8 アプリ**：4.3の6画面、モバイル回線への固定、溜めと再送。
  - 完了条件：エミュレータから、ローカルの中継を通して、偽の無線で動くPCに全部の操作ができる。モバイル回線への固定はエミュレータでは確かめきれないので、実機での確かめ方を `HARDWARE_TEST.md` に書く。
- **M9 通し**：PC（偽の無線）・中継（ローカル）・アプリ（エミュレータ）で、手動スキャン → 記録 → ラベル → 帯域ON/OFF → 歩測の送信まで通す。続けて、中継を止めて戻す、PCを再起動する、の2つで何も失わないことを確かめる。

## 7. やらないこと

- 送信を伴う機能、pcapの保存、通信の中身の解析、iOSアプリ。
- PCへの外からの接続（ポート開放、VPN、Tailscaleなどのトンネル）。Tailscaleは操縦用アプリとぶつかるため使わない。
- WebSocketや常時接続（VercelのHobbyでは、時間の上限と、接続中ずっとかかるメモリの課金に合わない）。
- 中継でのモード切替や、任意のコマンドの受け付け。
- 仕様書にない機能を足すこと。足したほうがよいと思ったら、`DECISIONS.md` に提案として書くだけにする。
